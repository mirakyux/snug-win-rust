# 应用切换及返回列表卡顿排查

## 发现

用户反馈 v1.0.3 点击应用和返回列表均卡顿，且整个电脑输入会停顿数秒。

本机运行日志显示普通导航反复切换 `1080×1900` 与 `1640×2884`。单次分辨率调用约 203–459 ms，部分随后重新调整 200% DPI，约 229–237 ms；窗口搬动另有约 0.5–1.3 秒。关闭按钮 UIA 查询约 0.9–2.3 秒，虽排在铺窗动作后面，仍占用同一个桌面操作队列。

代码与回归分别确认：

- `show_list` 将屏宽重置到基础宽，进入已放置窗口又恢复应用宽。三次列表/窗口往返会额外调用六次 `set_width`。
- 进入较小应用也会从基础宽开始，造成不必要的缩屏和后续扩屏。
- 原 `focus` 通过 `AttachThreadInput` 合并操作线程、当前前台和目标窗口的输入队列，再同步调用 `SetForegroundWindow`。这会扩大目标窗口阻塞的影响范围；日志没有单独记录它的耗时，不能将整机停顿全部归因于它。
- 显示区域查询重复枚举全部显示器，涉及 CCD、设备信息、DPI、注册表与 EDID；界面缩放、底栏和触控也各自重新查询。
- 关闭按钮查询可阻塞后续列表或撤屏操作；新增可控阻塞回归在旧实现上失败。

`set_width` 与 DPI 设置原本已有相等跳过。手机目标 DPI 固定为 200%，没有证据支持“每次无条件写 DPI”或“主动在 100%/200% 之间交替”的说法。

## 修复与取舍

- 用户随后指出字体被扩屏压小，明确要求分辨率手动设置、不得自动改动。最终手机/平板采用固定分辨率，应用最小尺寸也不触发扩屏；超宽应用明确提示尺寸受限，不自动缩字号。
- 设置中的每屏宽高以草稿编辑，只有“应用分辨率 / 恢复推荐”修改配置并生效；手动分辨率单独持久化，精确注册为单模式。当前机型推荐 1080×1900，触屏保持 200% DPI。
- 焦点操作只做 `SetForegroundWindow` 的尽力调用，不合并前台输入队列。
- 显示区域计算复用同一快照；一帧内缩放、底栏和触控共用完整屏幕与底栏矩形，无跨帧缓存。
- 关闭按钮查询移出操作队列，限制每 desk 同时只有一个查询，对返回结果核对当前目标并丢弃过期结果。
- 界面命令与状态快照轮询从 500 ms 改为 50 ms，原有 1/2/5 秒重探测门限保持不变。
- 输入钩子在加锁前直接放行物理鼠标与自身重放事件；按下命中使用已知界面、浏览器工具栏与气泡矩形，不在钩子回调中读取窗口、进程或文件。
- 15:34:37 实际已建屏，但旧 GUI 留在屏外且未处理退出请求。新增后台恢复路径，不要求主界面先出帧才能回到手机屏。

复用既有布局算式、操作队列和平台接口，未新增依赖，未改变 DPI 策略或删除模式切换后的等待。

## 验证边界

回归以实际显示模式写入次数、全量快照次数和阻塞期间队列能否继续处理为依据，不以仅检查最终尺寸代替性能行为验证。

用户确认退出 Snug 后鼠标恢复流畅；同一候选临时关闭手势、保持相同高分辨率后，切换明显改善，但本机鼠标仍有轻微卡顿。此对照支持输入钩子有明显影响，同时不能把所有延迟都归因于钩子。

当时单次显示器快照实测约 1 ms，短时 GPU 采样中 Snug 3D 约 7%、UU 3D 约 4%、编码约 1%，未显示满载；这些短样本不能排除瞬时停顿。扩大后的屏幕为 2060×3624，像素数量约为默认 1080×1900 的 3.6 倍，同时降低手机上的文字可读性。

同步跨进程搬窗仍可能等待目标程序。自动测试不能证明本机的整机停顿已消失，需安装最终固定分辨率候选后实际操作复核。
